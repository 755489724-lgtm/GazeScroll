# 万能翻页 · GazeScroll

> 用**前置摄像头**检测眨眼和点头/仰头，自动触发上滑翻页 —— 刷视频不用手。

---

## 这是什么

一个 Android 免手操作工具。它用前置摄像头实时检测你的**眼部与头部动作**，识别到指定动作后，通过无障碍服务模拟一次「向上滑动」，从而让抖音、B站等短视频信息流自动翻到下一个视频。

**适用场景**：吃饭、做饭、躺着、手上有东西、戴手套 —— 任何不方便碰屏幕的时候。

---

## ⚠️ 当前痛点（求社区大佬支招）

**目前必须借助一次 ADB 授权才能真正用起来。** 这是本项目最大的体验短板，也是我最希望社区帮忙解决的地方。

具体来说：

1. **自动开启无障碍服务需要 `WRITE_SECURE_SETTINGS` 权限。**
   这个权限是 `signature|privileged` 级别，普通 App 无法直接申请，只能通过 ADB 手动授予一次。
   代码里已经做了「授权一次后永久记住」的逻辑（`AccessibilityBootstrap.repairIfNeeded`），
   所以**只需要授权一次**，之后重启、升级都不用再来。

2. **用 `UsageStatsManager` 判断前台 App 也需要特殊授权。** 在 MIUI / HyperOS 上，
   `GET_USAGE_STATS` 的 appop 会被系统直接拒绝（日志里能看到 `ignore; rejectTime=…`），
   所以前台检测退化为「无障碍窗口列表 + 窗口标题」的方案。

3. **部分系统（如 HyperOS）会过滤第三方 App 的无障碍事件**，只有 launcher / systemui 的事件能收到。

### 如果你知道更好的方案，非常欢迎提 Issue 或 PR 🙏

我特别想知道：

- 有没有**免 ADB** 的方式让用户自己开启自定义无障碍服务？
- 有没有不依赖 `UsageStatsManager` 的可靠前台 App 检测方案？
- HyperOS / 澎湃 OS 上有没有绕过无障碍事件过滤的正当途径？

> 说明：本项目**不会**尝试任何 root、系统签名或跨应用越权方案。所有实现都基于公开的 Android 官方 API。

## 已实现功能

### 触发方式
- **眨眼翻页** —— 可配置连眨 1 / 2 / 3 次触发（默认 2 次）
  - 双眼开合度阈值 0.55（针对**戴眼镜**场景调过）
  - 单眼触发也生效；需连续 2 帧确认，避免误触
  - 两次眨眼间隔需在 200–1500ms 之间
  - 3 秒持续闭眼保护（防困倦误触）
- **点头 / 仰头翻页** —— 头部俯仰角超过 **8°** 且持续 **150ms**
  - 动态基准线：最近 45 帧的**中位数**（避免短促动作把基准带偏）
  - 支持下拉选择灵敏度（6° / 8° / 12°）
- **触发延迟（v4.8 起，实测有效）**：用相邻两帧的角度差算角速度，超过门限
  （俯仰 0.02°/ms、偏航 0.03°/ms，约 20°/秒）就**立即触发**，不再等「保持时间」。
  噪声撑不起 onset→阈值 这段行程、更达不到速度门限，所以快通道天然只放行真实动作。
  实测仰头延迟从 211~329ms 降到 **71~207ms**
  （`tiltUp triggered ... latency=71ms (fast, v=0.042°/ms)`）。
  保持时间同时也改为 `min(holdMs, motionWindowMs)`，永远不比对动作本身的要求更严格。
- **防误触（v4.8 起，v4.9 增强）**
  - **遮挡抑制，三条判据**（命中任一即抑制）：
    - `face lost` —— **脸突然消失又回来**。手掌/拳头整个盖住脸时人脸检测会直接丢失，
      这正是 v4.8 漏掉的路径（它只判「有人脸但没嘴」）。短暂丢失抑制 800ms，手指级
      遮挡抑制 500ms。
    - `mouth missing` —— 有人脸但读不出嘴的关键点（手挡下半脸）。
    - `face size jump` —— 人脸框尺寸一帧内变化 >35%（有东西贴上镜头）。
    日志：`occlusion detected (reason=face lost, faceLostFor=320ms) -> suppress 800ms`
  - **静止锁定 + 距离自适应（v4.9 引入，v5.5 调整作用对象）**：0.5 秒内俯仰/偏航峰峰值
    小于门限 → 认定人没在动。**门限本身按离手机多远缩放**：脸高占画面 ≥0.55（约 30cm）
    门限 ×2，≥0.38（约 50cm）门限 ×1.35。近距离时同样的微晃折算出的角度更大，固定门限挡不住，
    这就是「50cm 不误触、30cm 一动不动也误触」的成因。设置页可关闭。
    - ⚠️ **v5.5 修正**：静止锁定原本乘在**幅度阈值**上（×1.5），结果静止时点头要 9°~12°
      而不是 6°，用户反馈"点头很费劲"。现在它**改作用于速度门限**——
      噪声有幅度但没有速度，速度门限才是正确的工具；放大幅度只会把真实动作一起挡掉。
      缓存效果：动作幅度手感完全不变，静止时那点抖动过不了速度这一关。
  - **脸丢失即作废基准线**：150ms 就作废（以前 3 秒），手掠过脸一下不再污染基准线。
  - **距离档只有一个真值（v5.9）**：之前「近距离」有**两个**门槛 —— 点头省力增益用
    `faceRatio >= 0.50`，速度门限/静止峰峰值/静止硬锁定/眨眼收紧都用 `>= 0.55`。
    而用户 30cm 俯视实测落在 **0.45~0.55**，正好卡在两者之间，于是变成
    「**灵敏度按近距离给、防护按中距离算**」，而且档位在 0.50 附近**逐帧乱跳**
    （日志里 `nodBoost` 在 0.68/1.00、`distMode` 在 near/far 之间反复切）。
    现在只保留一个 `nearDistance`：`NEAR_ENTER_RATIO=0.46` / `NEAR_EXIT_RATIO=0.40`
    回差 + `faceRatio` 的 EMA 平滑，所有按距离缩放的东西全读它。
    门槛取 0.46 略低于实测区间下沿，保证 30cm 稳定判为近距离；50cm（0.37~0.41）与
    40cm（约 0.42~0.45）回不到近距离档，**远距离手感不变**。
    日志新增 `frSm`（平滑后的脸占比）与 `distance tier: …` 切换行。
  - **触发确认窗口：「v5.9 试过、v5.10 已撤销」（保留记录，避免重蹈）**
    v5.9 曾要求「阈值必须在最近 3 帧里至少 2 帧被越过」才允许触发，意图挡掉单帧跳变。
    带阶段标记的实机复测证明**必须撤销**：静止 90 秒里它一次都没派上用场
    （那段时间头部路径越阈值次数是 **0**，误触全部来自眨眼），却在正常使用中挡掉了
    **37 次**越阈值 —— 用户反馈「点头要更大的角度」「仰头点头要等 0.5 秒」「不像之前那么丝滑」。
    轻快的点头往往只跨一帧阈值，被它整个吃掉。
    **这是第三次踩同一个坑**（v5.5 的幅度放大、v5.7 的增益方向、本条的确认窗口）：
    凡是会连带拖慢真实动作的手段，都不能用来防误触。正确顺序是
    「先确定误触来自哪个检测器 → 再只动那一条链路」。
  - **误触到底从哪来（v5.10 实测定位）**：30cm 俯视静止 90 秒的误触**全部是眨眼**
    （诊断行 `lastTrigger=blink`，`blinks` 计数 90 秒内从 35 涨到 49），
    而两个叠加原因都很具体：① 设置里 `blinkTriggerCount` 实际是 **2**（以为是 3），
    于是任意两次自然眨眼间隔落在 0.2~1.5 秒内就翻页；② 近距离眨眼收紧没有生效
    （`BlinkDetector` 自己用 `faceRatio >= 0.55` 判断近距离，而 30cm 实测 0.49~0.51）。
    本版先把 ① 改成 3（零风险）；② 的收紧涉及「4 帧 ≈ 要求闭眼 235ms」，
    有挡掉有意眨眼的风险，留待下一版并用数据决定。
  - **最低速度门限（v5.0 引入，v5.5 叠加静止锁定与距离）**：即使幅度超过阈值，也必须走得够快
    （俯仰 ≥0.012°/ms、偏航 ≥0.015°/ms，再乘距离与静止系数）才允许触发。
    静止噪声**有幅度但没有速度**，所以被干净地挡掉；实测真实点头/仰头是 0.037~0.136°/ms，
    比门限高 3~11 倍，对正常动作零影响。这比抬高幅度阈值安全得多。
  - **幅度阈值不再被任何系数放大（v5.5 俯仰 / v5.8 偏航）**：
    `俯仰阈值 = 用户设定值 × 俯视增益`、`偏航阈值 = 用户设定值`。
    你设 6° 就是 6°，设"中 20°"就是 20°。诊断行的 `pitchTh` / `pitchThUp` / `yawTh`
    会显示当前实际生效值。
    - ⚠️ **v5.8 才把偏航轴也统一过来**：偏航阈值一直乘着距离系数，近距离
      （`faceRatio >= 0.45`）时**翻倍**——「中 20°」在 30cm 处实际是 **40°**，
      而用户的扭头幅度就是 40~52°，**刚好卡在门上**。实机日志：
      `turn triggered yaw=40.5°` 与 `yawTh=40.0°` 出现在同一时刻。
      这和 v5.5 在俯仰轴上修掉的是同一个错误：**用幅度阈值挡噪声是错的工具**，
      该管"够不够快"的是速度门限、该管"有没有在动"的是静止锁定。
      现在两个轴统一：幅度阈值就是用户设定值，距离只作用于速度门限与静止门限。
  - **扭头动作窗口（v5.8）**：`turnMotionWindowMs` 默认 **900ms**（原 600ms）。
    这个窗口对扭头先天太紧——扭头起点常有一段几乎不动的准备（脖子先转、脸还没跟上），
    这段被算进 rise，于是正常扭头会超窗被 `slow-rise` 判死（实机里这是最多的一类
    扭头拒绝：`yaw=54.4° speed=0.1496°/ms reason=slow-rise`）。
    "够不够快"交给速度门限，不由这个窗口定义。
  - **方向仲裁（v5.8）**：俯视姿态下扭头会带出 **±3~±10°** 的俯仰分量，
    而近距离点头阈值只有 **4.1°**（灵敏度 6°），所以扭头必然先把俯仰判定打穿——
    表现为「想左右扭头，结果变成上下滑」。远距离俯仰阈值是 6.0°，同样的分量常常够不到，
    所以远距离正常。
    判据**只看角速度**：真正的扭头是绕 Y 轴转动，偏航角速度必然明显；
    真正的点头是绕 X 轴转动，偏航角速度几乎为零。
    `|偏航速度| >= 0.006°/ms`（实测真实扭头中位数 0.0126、p90 0.158）时，
    点头/仰头一律让位；反向也对称地做了。
    - ⚠️ **仲裁绝不能用幅度当判据**。第一版加了 `yaw >= 阈值×0.6` 兜底，结果**把合格的
      扭头挡掉了**（`yaw=30.7° speed=0.2481°/ms reason=pitch-dominant-arbitration`）：
      扭头时偏航幅度本来就大，"幅度大"在这里恰恰证明是扭头，不是俯仰更强。
    - ⚠️ 仲裁必须用**本帧**的偏航读数。俯仰先于偏航评估，读上一帧会让耦合检测失灵
      （第二版就是这么错的）。见 `yawVelocityWith`。
    - ⚠️ **v5.11 收紧：光有 0.006°/ms 这一条绝对门限不够。** 30cm 处偏航读数的正常抖动
      （±1~3°）在实测约 11fps 下折算出来就有 0.01~0.03°/ms，轻松越线，于是"我在扭头"被
      误判。实机日志里用户明确在点头的那几秒，**连续 7 次点头被拒**，最后要用 −17.3° 的
      大幅点头才成功；阶段④ 一共 **39 次**俯仰候选被这条规则拒掉（点头 19、仰头 18），
      是最大的一类拒绝。现在要求三条同时成立：**① 偏航在动**（原门限）、
      **② 偏航速度 ≥ 俯仰速度**（"占优"的字面含义）、**③ 偏航幅度 ≥ 扭头阈值×0.3**。
      ②③ 是**闸门**而非替代：真实扭头（23~45°、0.13~0.25°/ms）照样让位，
      姿态抖动（±1~3°、0.01~0.02°/ms）不再误伤点头。
  - **回中锁定（v5.0 引入，v5.2 修复致命 bug）**：一次动作触发后，**反方向**要等头部回到
    中性区并稳定 150ms 才放行。修的是「仰头触发上滑后，把头放回正常位置的过程被判成点头，
    于是又下滑」——仰头时俯仰角为正，回正会经过 0 继续变负，天然长得像一次反向动作。
    - ⚠️ **v5.1 的这个锁会永久卡死**：中性区是相对基准线的 `±阈值×0.4`（默认 ±2.4°），
      而人的自然姿势常常长期偏离基准线（实测：俯仰角 -2.85°、基准线 3.69°，偏差 6.5°），
      **永远进不了中性区** → 锁永不解除 → 反向的点头被无限期屏蔽。
      用户反馈「仰头好用了，但点头全失效了」就是这个原因。
    - 修复：加 **400ms 最长锁定兜底**（回正动作本身只要几百毫秒），并让锁在头部静止时也能
      正常解除。日志会说明是哪条路径解除的。
  - **姿势偏置自动校正（v5.2）**：偏差越过死区、但始终没到阈值、且**持续 1.5 秒**时，
    判定为「换了姿势」而不是动作，把基准线渐进挪过去。
    这修的是 30cm 误触的**根本原因**：姿势缓慢变化（靠椅背、凑近屏幕）时滑动窗口中位数
    基准线跟不上，偏差被永久保留，白吃掉阈值余量——实测偏差 6.5° 正好贴在 ±6° 阈值上，
    静止噪声轻轻一推就越界。判据很干净：有意动作在 500ms 内就结束了，能维持 1.5 秒的是姿势。
  - **俯视姿态补偿（v5.4）**：大多数人是**俯视**看手机（手机在下方），俯仰角长期偏负。
    基准线若不跟着走，这个偏移会被当成"一直在低头"，于是往下动一点就误触、往上一动却
    不灵敏。现在相对基准线偏负 ≥3° 且**持续 2 秒**，就把基准线渐进迁到当前姿态，
    使后续点头/仰头以"当前俯视姿态"为中性点。
    判据基于**相对基准线**的偏移而非绝对角度，所以倒着拿手机、躺着看同样适用；
    只在俯仰轴生效，不碰扭头与眨眼。
    日志：`posture: looking down detected (held 2100ms, relative -6.2°), baseline gradually shifted to -14.8°`
  - **近距离点头增益（v5.6 引入，v5.7 收窄为单向，v5.12 增加俯视档）**：增益分三档，
    **仰头方向一律不动**：
    | 条件 | 系数 | 阈值（灵敏度设 6.0°） |
    |---|---|---|
    | 近距离 **+ 俯视** + 低头 | ×0.50 | **3.0°**（v5.12 新增） |
    | 近距离 + 低头 | ×0.68 | 4.1°（v5.6） |
    | 其他（含全部远距离、仰头方向） | ×1.00 | 6.0°（不变） |
    离手机近时（`faceRatio >= 0.50`，实测约 30~40cm）同样的颈部动作折算出的俯仰角更小，
    不补一点会明显更费力。**远距离完全不受影响** —— 新增档要求「近距 + 俯视」两条同时成立。
    - **v5.12 依据**：用户要的"轻点头"实测幅度是 **3.7~4.4°**，而 4.1° 的阈值卡在门上
      （`nodDown rejected: pitch=-3.7° threshold=4.1° reason=below-threshold`），
      所以"有时好使有时不好使"。压到 3.0° 后留出 0.7~1.4° 余量。
    - ⚠️ **v5.7 修正**：v5.6 把系数乘在了**共用的俯仰阈值**上，**仰头方向也一起吃到了**，
      于是近距离仰视被误触（灵敏度设 8° 时仰头只要 5.4°，设 6° 时只要 4.1°；
      实机日志里 45 次 tiltUp vs 14 次 nodDown，而被动仰视幅度正好是 4~7°）。
      现在改成**严格单向**：只在**低头方向**生效，抬头方向回到用户设定值。
      这正好实现「被动仰视不触发，主动仰头才触发」——被动仰视 4~7° 够不到 8°，
      主动仰头 9~11° 照样过。
      **不能用"抬高仰头阈值"来修**：那会把主动仰头一起挡掉。
    只压**幅度**阈值：速度门限、静止锁定、近距离静止硬锁定一律不动，
    所以"噪声有幅度没有速度"这道关卡照旧，**30cm 静止防误触逻辑未被触碰**。
    诊断行里 `pitchTh` 是**当前方向**的阈值、**`pitchThUp`** 是仰头方向的阈值：
    近距离看到 `pitchTh=5.4° pitchThUp=8.0°` 就说明单向增益生效。
    `nodBoost=0.68 nodBoostActive=true` 表示已生效（`nodBoost` 打的是**这一帧实际乘上去的
    系数**，与同一行的 `pitchTh` 永远自洽），触发日志会带 `boosted`。
    `distMode=near/far` 是增益的触发条件；别与同一行的 `dist=近/中/远`（握持距离档）混淆。
  - **晃动过滤：路径效率（v5.12）**：阈值压低之后必须挡住晃动（用户点名"地铁上近距离俯视
    晃动然后误触"）。判据是 `效率 = |净位移| / Σ|相邻差值|`：
    ```
    轻点头   0 → 1.0 → 2.5 → 3.5 → 4.2 → 4.2    路径 4.2   净位移 4.2   效率 1.00  ✅ 放行
    晃动   -1.5 → 1.2 → -1.0 → 2.8 → -1.2 → 3.2  路径 17.1  净位移 4.7   效率 0.27  ⛔ 拦下
    ```
    窗口 6 帧（约 0.5~0.7 秒），效率 <0.45 判为晃动。之所以不数"方向反转次数"：
    效率把幅度与次数合成一个量，少一个参数，对低频大幅晃动同样有效。
    效率值在诊断行 `shake=` 与候选拒绝日志里都能看到。
    - ⚠️ **它挡不住"急停/急刹"**：那一下是**单向**的，路径效率接近 1。
      v5.12 实测那次晃动误触就是 `tiltUp 8.1°`，效率判据没触发 —— 所以需要下面的加速度计。
  - **手机自身运动闸门（v5.13）**：`PhoneMotionMonitor` 读加速度计
    （优先 `TYPE_LINEAR_ACCELERATION`，没有就退回 `TYPE_ACCELEROMETER` + 低通减重力），
    线性加速度 ≥ **3.5 m/s²** 判定"手机被顿了一下"，之后 **600ms** 内所有俯仰/偏航候选
    一律不接受（理由 `phone-motion`）。
    物理依据：**点头是绕脖子转头（手机几乎不动），急停/急刹是整个人和手机一起顿**。
    摄像头分不出这两者（角度信号几乎一样），加速度计能。
    门限依据：坐着刷 **0~0.5 m/s²**、走路手持 **1.5~3**（用户明确说这种轻晃可接受）、
    急刹/突然停下 **4~15**，所以走路不会误伤，只有真正的顿挫才拦。
    传感器不可用时**失败开放**（`isMoving()` 恒 false），绝不因为读不到传感器就废掉手势。
    峰值在诊断行 `accel=`、状态在 `phoneMotion=`、可用性在 `accelReady=`。
  - **轻点头速度通道（v5.13）**：近距离 + 俯视 + 低头时，速度门槛从
    `FAST_PITCH_VELOCITY`（0.02）降到 **0.013**，并要求**多撑过一帧**（60ms，
    实测帧间隔 63~116ms ⇒ 等价于"下一帧仍须在阈值之上"），所以单帧跳变依旧进不来。
    依据：用户轻点头实测 **0.014~0.018°/ms**，够不到 0.02 就落到"保持"通道，
    而那条通道要求速度 ≥ 近距离门限 `0.024`（比 0.02 还高）—— **实际上永远走不通**，
    所以"不够快的点头一律无效"，日志里表现为 `reason=hold-not-met` 连着刷。
    通道条件与 ×0.50 增益完全一致，远距离与仰头方向不受影响。
  - **俯视判据：基准俯仰角（v5.12）**：`baselineDeg`（静止时人脸相对摄像头的绝对俯仰中位数）
    实测 **30cm 俯视 7.8~14.4、50cm 平视 0~2**，分离干净，且不需要任何新传感器 ——
    它本来就是基线学习中位数的输出。`posture=down/flat` 现在反映它。
  - **为什么"俯视"没有接进灵敏度开关（v5.6，实测结论）**：原本设想「下巴占比大 = 俯视」，
    用 `|下巴Y - 眼中心Y| / 脸高`（`chinRatio`）作判据。实机标定（平视/俯视/近距离俯视各 20 秒）后：
    远距 `chinRatio 0.335~0.368`，近距 `0.368~0.432` —— **它主要在反映距离，而不是姿态**，
    区分度不足以驱动灵敏度开关（原定的 0.68 门限从未达到）。
    所以增益最终**只用距离驱动**，俯视几何只作诊断保留（`chinRatio` / `chinMed` / `posture=`），
    等拿到"同距离下只改姿态"的干净数据再考虑启用。
    **不把区分度不足的信号接到灵敏度开关上**，是本条最重要的决定。
  - **近距离静止硬锁定（v5.3）**：faceRatio ≥0.55 且连续 1.2 秒内俯仰、偏航、眼睛开合度
    都没有实质变化 → 判定"人没在动、画面在抖"，关掉全部翻页判定，直到出现明显动作。
    判据刻意不用"方差"而用"稳定时长"，语义直观、用户可验证。
    日志：`staticHardLock=true, reason=close-distance stillness`
  - **眨眼判定按距离收紧（v5.3 设计，v5.11 才真正生效）**：ML Kit 的 `eyeOpenProbability`
    是**绝对**读数、不随脸的大小变化，但离得越近，睫毛/镜片反光/轻微眯眼的遮挡越明显。
    所以近距离时同时**降低闭眼阈值**（默认 0.55 → 中距 0.41 → 近距 0.30）并**提高连续帧要求**。
    只做一件事不够：阈值降太多会漏掉真实眨眼，而真实眨眼在近距离下持续帧数也更长，
    所以提高帧数对真实眨眼几乎无损。
    - ⚠️ **v5.11 之前它一直在空转**：`BlinkDetector` 用的是**自己**的 `faceRatio >= 0.55`，
      而用户 30cm 实测只有 **0.49~0.51**，所以从未进入近距离档（诊断行
      `blinkBelow=0.41 blinkFrames=2`）。实测静止 90 秒里的误触**全部**是 `lastTrigger=blink`
      —— 这就是「什么都没做视频自己跳」的来源。现在它读 **v5.9 那个统一的距离档**。
    - 连续帧要求取 **3 帧**（不是 v5.3 设计的 4 帧）：实测帧间隔 63~116ms（约 11fps），
      4 帧 ≈ 要求连续闭眼 360ms 以上，可能连**有意**眨眼一起挡掉；3 帧 ≈ 270ms 留一档余量。
      如果觉得"有意眨眼也变难了"，第一个要退的就是这个值。
  - **逐次眨眼诊断（v5.11）**：每次被计数的眨眼都打一行
    `I/Blink: blink #12 closure=280ms minEye=0.04/0.07 below=0.30 needFrames=3 gap=940ms run=2/3`
    —— 闭眼持续多久、眼睛最深读到多少、当前阈值与帧数、与上次的间隔、累计到几次。
    这是区分「有意眨眼」和「不由自主的眨眼」唯一可靠的依据。
  - **上一次翻页是谁触发的（v5.3）**：诊断行新增 `lastTrigger=blink/nod/tilt/turnL/turnR`
    与 `blinkBelow` / `blinkFrames`（当前实际生效的阈值与帧数要求）。
    排查"静止疯狂误触"时这是第一个要看的东西——只看触发次数无法区分来源。
  - 诊断行会打印 `faceRatio` / `dist`（近/中/远）/ `staticRange` / `staticLock` /
    `staticHardLock` / `recenterLock` / `downGaze` / `biasRecenter` / `occl` / `suppressMs` /
    `mouthForced` / `mouthRejected` / `lastTrigger` / `blinkBelow` / `blinkFrames` /
    `pitchTh` / **`pitchThUp`**（当前方向 / 仰头方向的实际生效阈值，v5.7）/ `yawTh` / `speedGate` /
    **`yawNow`** / **`pitchNow`** / **`pitchYielded`**（实时读数与仲裁结果，v5.8）/
    `chinRatio` / `chinMed` / `posture`（俯视几何，v5.6）/ `nodBoost` / `nodBoostActive` / `distMode`。

### 恢复能力（「隔一会重开抖音不触发」的防线，v5.3 起逐版加固）

这套失效最难对付的地方在于：**整条恢复链都挂在 `targetActive` 这一个布尔值上**，
它一旦错成 `false`，相机、看门狗、liveness 探针会被同一个条件一起挡住，谁也不去纠正它。

- **主动存活探针（v5.3）**：不再依赖"前台包名变化"事件，每 800ms 检查一次
  "允许翻页、但流水线实际是死的"并强制重新武装。下拉状态栏之所以"有效"，
  是因为它人为制造了两次包名变化替我们触发通知——现在不等用户动手。
- **电源状态自校正（v5.4）**：每 800ms 用 `PowerManager.isInteractive` 比对
  `screenActive`。HyperOS 可能丢掉息屏/亮屏广播，一旦丢了这个标志会永久停在错值上，
  而 `shouldAnalyze()` 会因此恒为 false。
- **`wasStale` 强制重绑（v5.6）**：不再信任 `cameraBound` 标志位，
  只要"很久没有帧"就强制重绑。
- **前台复核 fail-open（v5.7）**：**不信任自己记的前台**，直接向无障碍服务再问一次
  "现在活动的窗口是谁"；若它明确是目标应用、我们却认为不是且持续 2 秒，就强制重算。
  这是唯一一条不经过 `targetActive` 的恢复路径。
- **持续无画面硬重建（v5.7）**：用**独立于重绑**的计时（只在真的收到帧时清零）量
  "到底多久没画面"，持续 12 秒就丢弃 CameraX provider 重新获取。
  单靠每秒重绑是升不了级的——它每次都会把证据清零。
- **无障碍强制重绑（v5.5 引入，v5.7 改为按持续时长升级）**：`isConnected()` 只是
  `instance != null`，**实例存在不等于连接可用**。开关开着却超过 10 秒拿不到实例就直接
  `forceRebind`（关掉再打开），等价于用户手动下拉状态栏的效果。
- **全链路自检（v5.5）**：每 30 秒 + 每次亮屏打一行 `GazeSelfCheck`，一行说清卡在哪一环。
  v5.7 起还带 `a11yEvents` / `a11yEventAgoMs`（**系统到底有没有把窗口事件发给我们**）、
  `hardResyncs` / `noFrameForMs`。
  这几个字段的关键在于能区分两个完全不同的病因：
  **`a11yEvents` 停涨 = 系统根本没发事件（只能靠轮询兜底）；
  计数在涨但前台判错 = 我们自己的判据有问题。** 只看 `foreground=` 是分不出来的——
  那是我们对事件的*理解*，不是事件本身。
- **日志标记**：`foreground change: A -> B (target=…)`、
  `rebind reason=user-present/app-switch/no-frame`、
  `pipeline resync (app-switch): forcing rebind`、
  `rebind reason=user-present -> ACTION_USER_PRESENT full restart`。
- **张嘴点击的健壮性（v5.0）**
  - **基准合理性检查**：手挡脸、半张脸出画会读出极小的比值（实测抓到 **0.114**，正常
    闭嘴是 0.205~0.23）。一旦它进了基准窗口，基准就被永久带偏 —— 之后所有正常读数都比
    它高出阈值，于是检测器**一直以为用户在张嘴**，表现为「功能要开关一次才能用」。
    现在不合理的样本直接不采纳（`mouthRejected` 计数可见）。
  - **卡死自愈**：连续判定"张嘴"超过 4 秒（没人能张这么久）就判定基准坏了，强制重学
    （`mouthForced` 计数可见）。
  - **遮挡后重学**：遮挡判定命中时连张嘴检测器一起复位。
  - **点击失败也计数**：以前只有注入成功才 +1，所以界面上「已点击 0 次」既可能是没识别
    到张嘴、也可能是识别到了但注入失败 —— 两种问题排查方向完全不同，现在分开显示并
    在通知里给出后端名。
  - 日志：`mouth open detected ... -> tap, rearm after mouth closes` /
    `mouth rearmed: closed again, ready for next tap`
- **张嘴 → 点击屏幕中央（v4.6 新增，默认开启）**
  - 张嘴一次 = 在屏幕中央注入一次单击。抖音这类全屏播放器收到单击就是**暂停 / 播放视频**
  - **不暂停本 App**：张嘴之后眨眼、点头、左右扭头照常翻页
  - 判定量是「嘴到鼻底的距离 ÷ 人脸高度」，并**按你本人自然闭嘴的水平自动校准**
  - 灵敏度三档 5% / 8% / 12% 脸高
  - **防连发**：必须「闭嘴之后再次张嘴」才算下一次，一直张着嘴只会点一下
- **上下滑动自适应（v4.5）+ 柔度可调（v4.6）**
  - 抖音是「一屏一个视频」，微博 / 小红书是连续列表，同样幅度的手势在前者刚好、后者会滚过好几屏
  - 按当前前台应用自动切换幅度与时长：
    | 应用 | 滑动距离 | 时长 |
    | --- | --- | --- |
    | 抖音 / 快手等整屏视频 | **39% 屏高** | **150ms** |
    | 微博 / 小红书 / 知乎 / B站等列表 | **可调**，默认 26% 屏高 | 420ms |
    | 其他 | 40% 屏高 | 300ms |

  - ⚠️ **抖音那一档是 v5.0/v5.1 实机逐组标定出来的**，不是"一屏一个视频就划一整屏"想当然。
    90%/130ms、60%/400ms、45%/350ms、50%/700ms 全部无效，**只有 39%/150ms 被接受**。
  - **手势路径必须有中间点（v5.1）**：`dispatchGesture` 的一条直线相当于"一个采样点从起点
    直接跳到终点"，很多 App 的滚动手势识别看不到足够的坐标更新就把它忽略了 —— 现象正是
    「日志 `swipe ok=true` 但页面纹丝不动」。现在纵向滑动会补 6 个均匀分布的中间点，
    让系统派发多次 MOVE 事件。已用截屏像素对比验证生效（设置页 ScrollView 被真实滚动）。
  - **自定义滑动柔度**：滑块调列表类的幅度（10%–50%，每档 2%），默认 26% 与 v4.5 手感一致，附「恢复默认」
  - 参数全部是**屏幕高度的比例**，不写死像素；左右扭头不参与自适应
- **左右扭头滑动（v4.4 新增，默认关闭）** —— 头部偏航角超过阈值并保持一下，向对应方向滑一次
  - 灵敏度三档：14° / 20° / 28°
  - 前后左右**共用同一个冷却**，所以不可能出现上下左右同时滑动
  - 前置摄像头画面是镜像的，符号已在检测器里翻正；方向反了可在设置里一键反转
- **防误触冷却（v4.3 新增，默认开启 1.5 秒 / 可调 0.5–5 秒）**
  - 摄像头逐帧（约 15fps）检测，一次真实动作会连续命中好几帧，点头时眼睛还会被连带判成眨眼
  - 眨眼和点头**共用同一个全局冷却计时器**：任意一个动作触发翻页后，冷却期内所有信号一律忽略
  - 触发点统一收敛到 `GazeCameraService.fireSwipe()`，两个检测器无法互相绕过

### 功耗与运行策略
- **按需启停**：只有在你选定的目标 App 处于前台时才开摄像头，切走立刻释放
- **全局使用翻页（v4.7 新增，默认关闭）**：打开后白名单整个跳过，桌面 / 系统设置 / 任何 App
  都能翻页（代价是摄像头一直工作）。设置页实时显示当前前台应用。
- **切回目标应用必定恢复（v4.7 修复，v5.3 才真正彻底）**
  - v4.7 加过「强恢复」，但整条恢复链只在**前台包名发生变化**时才触发：
    `commitPending` 里有一句 `if (!force && packageName == foregroundPackage) return`。
    于是出现死角——状态里记的前台已经是抖音时（或这次切换没被观察到），**包名没变 →
    什么都不通知 → 相机不重绑 → 功能静默失效**。
  - 这解释了那个"老毛病"：**隔一会重新打开抖音必须下拉状态栏才生效**。下拉状态栏"有效"
    是因为它**人为制造了两次包名变化**（先变成 `com.android.systemui`，收起时再变回抖音），
    等于替我们触发了两次通知。
  - v5.3 改成**主动存活探针**：`AppStateManager` 每 800ms 轮询时直接问服务「你现在真的
    在跑吗」，不再依赖任何窗口事件。三级递进恢复：
    1. 应分析却无帧 → 强恢复（重绑相机）；
    2. 连续多次仍无帧 → 丢弃 provider 重新获取（相机被别的进程占着时必需）；
    3. 再不行 → 重建整条服务管线。
  - 服务实例不存在时探针会直接把它拉起来。日志：`liveness probe: ... -> recovering`。
- **息屏唤醒（v5.4 彻底修复）**
  - v5.3 的探针解决了"恢复没被触发"，但**恢复本身还可能被一个错误的标志挡住**。
    `screenActive` 只在收到息屏/亮屏广播时更新，而 HyperOS 省电策略下这些广播**可能被丢掉**：
    一旦丢了，标志永久停在错误值上 → `shouldAnalyze()` 永远返回 false →
    什么都不分析，而且探针 / 看门狗 / 强恢复**全被这一个条件挡住**。
  - **电源状态自校正**：每 800ms 用系统自己的 `PowerManager.isInteractive`（真相来源，
    不受广播影响）与标志比对，不一致就纠正并触发一次亮屏恢复。
    日志：`power state correction: screenActive=... but isInteractive=...`
  - **解锁事件**：除 `ACTION_SCREEN_ON` 外还监听 `ACTION_USER_PRESENT`——亮屏但锁屏时
    相机拍到的是锁屏画面，恢复动作放在解锁后更准。
  - 亮屏后做一次**完整重建**（而不是"检查后补齐"）：作废全部检测器与抑制状态 →
    丢弃 provider 重新获取 → 失败按 **500 / 1000 / 2000ms** 退避重试。
  - 顺带修掉一个隐私问题：息屏广播丢失时相机原本会在**屏幕已熄灭的情况下继续运行**，
    现在会被自校正纠正回来。
- **三级功耗模型**：
  | 状态 | 行为 |
  | --- | --- |
  | 运行 | 全速分析（约 15fps） |
  | 温机 | 保留相机、丢弃帧、ML Kit 空闲（30 秒窗口） |
  | 释放 | 完全关闭相机 |
- 息屏自动释放相机
- 前台服务通知实时显示「运行中 / 待机」

### 方式二：自己编译

```bash
git clone https://github.com/755489724-lgtm/GazeScroll.git
cd GazeScroll
./gradlew assembleDebug
```

环境要求：JDK 17、Android SDK（compileSdk 34 / buildTools 34.0.0）、Gradle 8.9。

> 仓库里目前只有 `gradle/wrapper/gradle-wrapper.properties`，**没有 wrapper 脚本与 jar**。
> 用 Android Studio 打开会自动补齐；命令行编译请先执行一次 `gradle wrapper`。

### 🔑 必须的 ADB 授权步骤（只做一次）

手机开启「USB 调试」连上电脑后，执行：

```bash
# 1) 授予 WRITE_SECURE_SETTINGS —— 用于自动开启无障碍服务
adb shell pm grant com.example.gazescroll android.permission.WRITE_SECURE_SETTINGS

# 2) 允许后台弹出界面（部分机型需要）
adb shell appops set com.example.gazescroll SYSTEM_ALERT_WINDOW allow

# 3) 前台 App 检测（MIUI/HyperOS 上可能被系统拒绝，属于已知问题）
adb shell appops set com.example.gazescroll GET_USAGE_STATS allow

# 4) 手动把无障碍服务加进启用列表
adb shell settings put secure enabled_accessibility_services \
  com.example.gazescroll/com.example.gazescroll.GazeAccessibilityService
adb shell settings put secure accessibility_enabled 1

# 5) 启动
adb shell am start -n com.example.gazescroll/.MainActivity
```

**授权完成后就可以拔掉数据线了**，之后正常使用不需要再连电脑。

> 项目里附带了一个 `恢复翻页.bat`（Windows），会把上面这几步 + 重装 + 启动一次性做完，
> 适合手机重启后或服务掉线时一键恢复。

### 使用

1. 打开 App，勾选你要生效的 App（比如「抖音」）
2. 点「启动」
3. 切到抖音，开始刷 —— 眨眼、点头、仰头或扭头即可翻页
4. 灵敏度不合适就在 App 里调，面板上能看到实时数据

### 设置项一览

| 分组 | 设置项 | 说明 |
| --- | --- | --- |
| 触发方式 | 眨眼次数 | 连眨 1 / 2 / 3 次触发（默认 2） |
| | 点头 / 仰头开关 | 低头 = 上一个，仰头 = 下一个 |
| | 反向俯仰 | 点头仰头反了就打开 |
| | 静止防误触 | 人不动时自动抬高阈值 |
| 防误触冷却 | 启用冷却时间 | 眨眼与点头共用一个计时器 |
| | 冷却时长 | 0.5–5 秒滑块（默认 1.5 秒），实时显示倒计时 |
| 左右扭头 | 开关 + 灵敏度 | 14° / 20° / 28°，默认中 20° |
| | 反转左右方向 | 扭头方向反了就打开 |
| 张嘴点击 | 开关 + 灵敏度 | 5% / 8% / 12% 脸高，默认中 |
| 自适应滑动 | 开关 | 按前台应用切换幅度与时长 |
| | 自定义滑动柔度 | 列表类 10%–50% 屏高，默认 26%，可恢复默认 |
| | 当前滑动配置 | 实时显示识别到的应用与生效参数 |
| 全局使用翻页 | 开关 | 桌面 / 任意应用都能触发 |
| 生效的应用 | 多选列表 | 节能白名单；全部不勾选 = 全局生效 |
| 实时数值 | 诊断面板 | 见下 |

**实时数值面板**能直接读到：人脸占比与距离档、俯仰/偏航角与基准线、张嘴比例与本人闭嘴基准、
当前滑动配置、冷却倒计时、静止/回中锁定状态。挑灵敏度就照着这里的真实数字选，不用猜。

## 已知限制

- **必须 ADB 授权一次**（见上）
- MIUI / HyperOS 上 `GET_USAGE_STATS` 被系统拒绝，前台检测降级为窗口标题方案
- HyperOS 会过滤第三方 App 的无障碍事件，只放行 launcher / systemui 的事件
- `am force-stop` 会**清空** `enabled_accessibility_services`，服务需要重新拉起
  （用 `恢复翻页.bat` 或重新打开 App 即可）
- 部分机型需要同时开启「USB 调试(安全设置)」才能正常注入手势
- 强光 / 逆光 / 大幅晃动时检测率会下降

## 项目结构

```
app/src/main/java/com/example/gazescroll/
├── BlinkDetector.kt               眨眼状态机（纯逻辑，无 Android API）
├── HeadPoseDetector.kt            头部姿态状态机（俯仰点头/仰头 + 偏航左右扭头，速度驱动、静止锁定、距离自适应）
├── MouthOpenDetector.kt           张嘴检测（嘴到鼻底距离 / 脸高，含本人闭嘴基准与防连发锁存）
├── AdaptiveSwipe.kt               按前台应用自适应的纵向滑动参数表 + 柔度档位换算
├── GlobalTriggerGate.kt           全局触发冷却闸门（各触发方式共用，防一次动作多触发）
├── GazeStateMachine.kt            早期「下看上扫」两区状态机（仅调试用）
├── FaceGazeAnalyzer.kt            CameraX ImageAnalysis + ML Kit → 分析结果
├── GazeCameraService.kt           前台服务（type=camera），持有整条流水线
├── GazeAccessibilityService.kt    无障碍服务，负责 dispatchGesture 注入上滑
├── AccessibilityBootstrap.kt      自动开启/修复无障碍服务（免手动去设置里点）
├── AppStateManager.kt             前台 App 检测 + 状态机启停
├── SwipeInjector.kt               手势注入抽象层（Shizuku 优先，无障碍兜底）
├── ShizukuSwipeDispatcher.kt      Shizuku 注入路径（shell 权限，最接近真实手指）
├── TargetApps.kt                  目标 App 列表与安装检测
├── AppPrefs.kt / GazeModel.kt     配置持久化与数据模型
└── MainActivity.kt                极简配置界面

app/src/main/res/xml/accessibility_service_config.xml
tools/                             实机测试脚本与配置样例（标定参数时用）
```

技术栈：**Kotlin** · CameraX 1.3.4 · ML Kit face-detection 16.1.7（bundled）· AccessibilityService · 原生 View

### 实机标定工具

`tools/` 下是标定时用的脚本，对 App 本身无影响：

- `verify-gesture.ps1` —— 用**截屏像素对比**验证注入手势是否真的生效（不依赖人眼看屏幕）
- `verify-slider.ps1` —— 验证设置项持久化链路
- `gz_prefs_test.xml` / `gz_prefs_slider.xml` —— 直接写入 SharedPreferences 的配置样例

触发参数可以用广播逐组实测（`BuildConfig.DEBUG` 限定）：

```bash
adb shell am broadcast -a com.example.gazescroll.action.TEST_SWIPE \
  -p com.example.gazescroll --ef from 0.70 --ef to 0.30 --el duration 150
```

抖音的 39%/150ms 就是用这个通道逐组试出来的（80%、90%、60%、45%、50% 全部无效）。
